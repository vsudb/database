
*Проектирование БД* — это системный процесс трансформации **неструктурированных требований реального мира** в **оптимизированную и надежную структуру хранения данных**. Чтобы избежать архитектурных ошибок, процесс делят на четкие этапы и уровни абстракции.


### Этапы проектирования БД:

1. **Определить предметную область:** Сформулировать, какую бизнес-задачу решает система.
2. **Выделить сущности:** Найти ключевые объекты (`Студент`, `Предмет`, `Преподаватель`), которые в дальнейшем станут таблицами.
3. **Определить атрибуты:** Зафиксировать свойства каждой сущности (`Имя`, `Email`, `Название`) поля/колонки таблицы.
4. **Назначить первичные ключи (Primary Key):** Выбрать уникальные идентификаторы.
5. **Определить связи:** Установить мощности связей (`1:1`, `1:N`, `M:N`).
6. **Задать внешние ключи (Foreign Key):** Разрешить связи между таблицами.
7. **Провести нормализацию:** 
 - Исключить избыточность информации(дублирование) 
 - обеспечить целостность данных (устранить аномалии записи/удаления) (1NF–3NF).

**Какие проблемы решает нормализация?**

*Если хранить все данные в одной огромной таблице (как в Excel), возникают три основные проблемы (аномалии):*

- **Повторение данных (избыточность):**

Например, если один и тот же клиент сделал 100 покупок, вам придется 100 раз записывать его имя, телефон и адрес. Это тратит память.
- **Аномалия обновления:** 

Если клиент изменит номер телефона, придется искать все 100 записей и менять телефон в каждой. Если хоть одну пропустить — данные станут противоречивыми.

- **Аномалия удаления:** 

Если клиент отменит свой единственный заказ и вы удалите строку, вы вместе с заказом случайно сотрете и самого клиента (его имя и телефон).

8. **Реализовать в SQL:** Написать DDL-скрипты для конкретной СУБД.

## Три уровня абстракции 
Согласно стандарту ANSI/SPARC, процесс проектирования разделяется на три уровня абстракции. Это позволяет разделить зоны ответственности между бизнес-аналитиками, архитекторами и DBA.


```

+-------------------------------------------------------------------+
| 1. КОНЦЕПТУАЛЬНЫЙ УРОВЕНЬ                                         |
| Бизнес-модель: Сущности и связи (ER-диаграмма)                    |
+-------------------------------------------------------------------+
│
▼
+-------------------------------------------------------------------+
| 2. ЛОГИЧЕСКИЙ УРОВЕНЬ                                             |
| Реляционная модель: Таблицы, PK/FK, Нормализация (3NF)            |
+-------------------------------------------------------------------+
│
▼
+-------------------------------------------------------------------+
| 3. ФИЗИЧЕСКИЙ УРОВЕНЬ                                             |
| Реализация в СУБД: DDL (SQL), Типы данных, Индексы, Хранение      |
+-------------------------------------------------------------------+

```

## 5. Практический сквозной пример

Рассмотрим предметную область **«Университет: Студенты и Предметы»**.

### Этап 1: Концептуальная модель
* **Сущности:** `Студент`, `Предмет`.
* **Связь:** Студент может изучать много предметов, на предмет могут ходить много студентов (**M:N**).

---

### Этап 2: Логическая модель
Для реализации связи **M:N** создаем промежуточную сущность `Студент_Предмет`.

* **Таблица `Students`**:
  * `student_id` (PK)
  * `full_name` (String)
* **Таблица `Subjects`**:
  * `subject_id` (PK)
  * `title` (String)
* **Таблица `Student_Subjects` (Junction Table)**:
  * `student_id` (FK ──> Students.student_id)
  * `subject_id` (FK ──> Subjects.subject_id)
  * `PRIMARY KEY (student_id, subject_id)`

---

### Этап 3: Физическая модель (PostgreSQL)

```sql
-- 1. Таблица студентов
CREATE TABLE students (
    student_id SERIAL PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- 2. Таблица предметов
CREATE TABLE subjects (
    subject_id SERIAL PRIMARY KEY,
    title VARCHAR(100) NOT NULL
);

-- 3. Промежуточная таблица связи M:N (Junction Table)
CREATE TABLE student_subjects (
    student_id INT NOT NULL REFERENCES students(student_id) ON DELETE CASCADE,
    subject_id INT NOT NULL REFERENCES subjects(subject_id) ON DELETE CASCADE,
    enrolled_at DATE DEFAULT CURRENT_DATE,
    PRIMARY KEY (student_id, subject_id)
);

-- Индекс для ускорения поиска студентов по предмету
CREATE INDEX idx_student_subjects_subject ON student_subjects(subject_id);

```

## Типичные ошибки при проектировании

1. **Пропуск концептуального этапа:** Попытка сразу проектировать таблицы приводит к упущенным бизнес-требованиям.
2. **Прямая реализация M:N:** Попытка записать массив/список ID через запятую в одну ячейку (нарушение 1NF).
3. **Преждевременная денормализация:** Нарушение нормальных форм «ради скорости» еще до того, как появилась реальная проблема с производительностью.
4. **Смешение логического и физического уровней:** Использование типов данных конкретной СУБД на ранних этапах обсуждения бизнес-логики.

## Смысловой вектор движения(pipeline) при создании базы данных:

**Реальный мир ──> Предметная область ──> Сущности ──> Атрибуты ──> Ключи ──> Связи ──> Нормализация ──> SQL**
