# Типы связей (Relationships) в базах данных


При проектировании реляционных баз данных (RDBMS) одной из главных задач является правильное определение **связей (отношений)** между таблицами. Связи указывают, как данные из одной таблицы соотносятся с данными из другой, обеспечивая целостность и логическую структуру базы данных.

Данный документ содержит полное руководство по типам связей с наглядными текстовыми диаграммами, таблицами и примерами на языке **SQL**, основанными на схеме университета.

---

## Основные концепции

* **Primary Key (Первичный ключ, PK)** — уникальный идентификатор записи в таблице (например, `univ_id`, `student_id`).
* **Foreign Key (Внешний ключ, FK)** — поле в одной таблице, ссылающееся на первичный ключ в другой таблице.

---

## 1. Связь «Один к одному» (One-to-One / 1:1)

### Описание
Каждая запись в **Таблице А** соответствует **ровно одной** записи в **Таблице Б**, и наоборот.

### Студент ↔ Паспортные данные (`student` ↔ `student_passports`)
* **Связь/Логика**: У одного студента может быть только один паспорт, и конкретный паспорт принадлежит ровно одному студенту.

```text
student                       student_passports
+------------+---------+     +-------------+--------------+------------+
| student_id | surname |     | passport_id | passport_num | student_id |
+------------+---------+     +-------------+--------------+------------+
| 1          | Аня     |1---1| 101         | 4510 123456  | 1          |
| 2          | Боря    |1---1| 102         | 4511 654321  | 2          |
| 3          | Вера    |1---1| 103         | 4512 789012  | 3          |
+------------+---------+     +-------------+--------------+------------+
```

### **Когда использовать**:
* Разделение таблицы на части (вынос редко используемых полей в отдельную таблицу).
* Хранение конфиденциальных данных с настройкой отдельных прав доступа.
* Оптимизация производительности (уменьшение размера строки основной таблицы).

### **Реализация в SQL**:
  В дочерней таблице `student_passports` внешний ключ `student_id` помечается ограничением `UNIQUE` (уникальность).

  
  Это гарантирует, что на один ID студента нельзя добавить более одной записи с паспортом.

```sql
CREATE TABLE student_passports
(
    passport_id  INT NOT NULL,
    student_id   INT NOT NULL UNIQUE, -- UNIQUE обеспечивает связь 1:1
    passport_num VARCHAR(20) NOT NULL,
    issue_date   DATE,
    issued_by    VARCHAR(160),
    PRIMARY KEY (passport_id),
    CONSTRAINT fk_student_passport
        FOREIGN KEY (student_id) REFERENCES student (student_id)
        ON DELETE CASCADE
);
```

## 2. Связь «Один ко многим» (One-to-Many / 1:N)

### Описание
Каждая запись в родительской таблице может соотноситься с **несколькими** записями в дочерней таблице, но запись в дочерней таблице относится только к **одной** записи из родительской.

### 2.1. Университет → Преподаватели
* **Связь**: Один университет может иметь много преподавателей, но каждый преподаватель работает только в одном университете.

```text
university                    lecturer
+---------+-------------+     +-------------+-----------+---------+
| univ_id | univ_name   |     | lecturer_id | surname   | univ_id |
+---------+-------------+     +-------------+-----------+---------+
| 1       | МГУ         |<----| 101         | Иванов    | 1       |
| 2       | СПбГУ       |<----| 102         | Петров    | 1       |
+---------+-------------+     | 103         | Сидоров   | 2       |
                              +-------------+-----------+---------+
```

**Реализация в схеме:**
```sql
ALTER TABLE lecturer
    ADD CONSTRAINT univlect_for_key
        FOREIGN KEY (univ_id) REFERENCES university (univ_id);
```
* `univ_id` в `lecturer` — внешний ключ.
* Один `univ_id` → много `lecturer_id`.
* Один `lecturer_id` → только один `univ_id`.

---

### 2.2. Университет → Студенты
* **Связь**: Один университет может иметь много студентов, но каждый студент учится только в одном университете.

```text
university                    student
+---------+-------------+     +------------+---------+---------+
| univ_id | univ_name   |     | student_id | surname | univ_id |
+---------+-------------+     +------------+---------+---------+
| 1       | МГУ         |<----| 1          | Аня     | 1       |
| 2       | СПбГУ       |<----| 2          | Боря    | 1       |
+---------+-------------+     | 3          | Вера    | 2       |
                              +------------+---------+---------+
```

**Реализация в схеме:**
```sql
ALTER TABLE student
    ADD CONSTRAINT univ_for_key
        FOREIGN KEY (univ_id) REFERENCES university (univ_id);
```

## 3. Связь «Многие ко многим» (Many-to-Many / M:N)

### Описание
Каждая запись в **Таблице А** соотносится с **несколькими** записями в **Таблице Б**, и наоборот. Напрямую в реляционных БД не создается — всегда реализуется через **промежуточную (связующую) таблицу**.

### 3.1. Преподаватели ↔ Предметы (через `subj_lect`)
* **Связь**: Один преподаватель может вести много предметов, один предмет могут вести несколько преподавателей.

```text
lecturer              subj_lect                subject
+-------------+       +-------------+---------+    +---------+-----------+
| lecturer_id |       | lecturer_id | subj_id |    | subj_id | subj_name |
+-------------+       +-------------+---------+    +---------+-----------+
| 101         |<------| 101         | 1       |--->| 1       | Математика|
| 102         |<------| 101         | 2       |--->| 2       | Физика    |
+-------------+       | 102         | 1       |--->| 1       | Математика|
                      +-------------+---------+    +---------+-----------+
```

**Реализация в схеме:**
```sql
CREATE TABLE subj_lect (
    lecturer_id int NOT NULL,
    subj_id     int NOT NULL
);

ALTER TABLE subj_lect
    ADD PRIMARY KEY (lecturer_id, subj_id);

ALTER TABLE subj_lect
    ADD CONSTRAINT lect_for_key
        FOREIGN KEY (lecturer_id) REFERENCES lecturer (lecturer_id);

ALTER TABLE subj_lect
    ADD CONSTRAINT subj_for_key
        FOREIGN KEY (subj_id) REFERENCES subject (subj_id);
```
* **Особенность**: `subj_lect` — это чистая связующая таблица (junction table), без дополнительных атрибутов. Составной первичный ключ `(lecturer_id, subj_id)` гарантирует уникальность пары.

---

### 3.2. Студенты ↔ Предметы (через `exam_marks`)
* **Связь**: Один студент сдаёт много предметов, один предмет сдают много студентов.

```text
student              exam_marks               subject
+------------+       +----------+------------+    +---------+-----------+
| student_id |       | exam_id  | student_id |    | subj_id | subj_name |
+------------+       +----------+------------+    +---------+-----------+
| 1          |<------| 1        | 1          |--->| 1       | Математика|
| 2          |<------| 2        | 1          |--->| 2       | Физика    |
+------------+       | 3        | 2          |--->| 1       | Математика|
                     +----------+------------+    +---------+-----------+
```

**Реализация в схеме:**
```sql
CREATE TABLE exam_marks (
    exam_id    int NOT NULL,
    student_id int NOT NULL,
    subj_id    int NOT NULL,
    mark       int,
    exam_date  DATE
);

ALTER TABLE exam_marks
    ADD PRIMARY KEY (exam_id, student_id, subj_id);

ALTER TABLE exam_marks
    ADD CONSTRAINT student_for_key
        FOREIGN KEY (student_id) REFERENCES student (student_id);

ALTER TABLE exam_marks
    ADD CONSTRAINT subject_for_key
        FOREIGN KEY (subj_id) REFERENCES subject (subj_id);
```

## 4. Связь через ассоциативную сущность (Associative Entity)

Таблица `exam_marks` — это классический пример **ассоциативной сущности**. В отличие от «чистой» таблицы связи `subj_lect`, она не только связывает `student` и `subject`, но и хранит собственные бизнес-данные об экзамене.

### Структура атрибутов `exam_marks`:

| Поле | Роль |
| :--- | :--- |
| `exam_id` | Идентификатор экзамена (часть PK) |
| `student_id` | Внешний ключ → `student` |
| `subj_id` | Внешний ключ → `subject` |
| `mark` | Оценка (доп. атрибут) |
| `exam_date` | Дата экзамена (доп. атрибут) |

### Схема взаимодействия:

```text
         student                    subject
            |                          |
            |  M                    N  |
            +--------> exam_marks <----+
                       (associative)
                    +----+----+----+----+
                    |mark|date| ...| ...|
                    +----+----+----+----+
```

## 5. Рекурсивная связь / Самоссылающаяся связь (Self-Referencing / Hierarchy)

### Описание
Таблица ссылается сама на себя. Внешний ключ (Foreign Key) указывает на первичный ключ (Primary Key) **той же самой таблицы**. Используется для моделирования иерархических и древовидных структур.

---

### 5.1. Студент и Староста (`student` ↔ `student`)
* **Логика**: Староста группы — это один из студентов. Каждому студенту назначается его староста (другой студент из этой же таблицы).

```sql
-- Добавление поля leader_id в таблицу student
ALTER TABLE student
    ADD COLUMN leader_id INT NULL;

-- Создание внешнего ключа, ссылающегося на эту же таблицу
ALTER TABLE student
    ADD CONSTRAINT fk_student_leader
        FOREIGN KEY (leader_id) REFERENCES student (student_id);
```

---

### 5.2. Иерархия руководства (Лектор ➔ Зав. кафедрой ➔ Декан)
* **Логика**: Обычный лектор подчиняется заведующему кафедрой, а заведующий кафедрой — декану факультета. При этом декан, заведующий кафедрой и лектор являются записями в одной таблице `lecturer`.

```sql
-- Добавление поля manager_lecturer_id для указания прямого руководителя
ALTER TABLE lecturer
    ADD COLUMN manager_lecturer_id INT NULL;

-- Создание внешнего ключа, ссылающегося на этой же таблицы
ALTER TABLE lecturer
    ADD CONSTRAINT fk_lecturer_manager
        FOREIGN KEY (manager_lecturer_id) REFERENCES lecturer (lecturer_id);
```

**Логика уровней подчинения:**
* **Декан (Верхний уровень)**: `lecturer_id = 1`, `surname = 'Иванов'`, `manager_lecturer_id = NULL` *(наивысшее звено, никому не подчиняется)*.
* **Зав. кафедрой (Средний уровень)**: `lecturer_id = 2`, `surname = 'Петров'`, `manager_lecturer_id = 1` *(подчинен Декану с ID = 1)*.
* **Лектор (Нижний уровень)**: `lecturer_id = 3`, `surname = 'Сидоров'`, `manager_lecturer_id = 2` *(подчинен Зав. кафедрой с ID = 2)*.

---

### 5.3. Классическая иерархия Сотрудников и Менеджеров (`employee`)
* **Логика**: В любой организации у сотрудника есть начальник (менеджер), который также является сотрудником компании.

```sql
-- Создание таблицы сотрудников с рекурсивной связью
CREATE TABLE employee
(
    emp_id     INT NOT NULL PRIMARY KEY,
    surname    VARCHAR(60) NOT NULL,
    name       VARCHAR(60) NOT NULL,
    position   VARCHAR(60),
    manager_id INT NULL, -- Ссылка на emp_id руководителя
    CONSTRAINT fk_employee_manager
        FOREIGN KEY (manager_id) REFERENCES employee (emp_id)
);
```

## 6. Сводная таблица типов связей

| Тип связи | Название | Расположение Foreign Key (FK) | Пример SQL / Концепция |
| :--- | :--- | :--- | :--- |
| **1 : 1** | Один к одному | В дочерней таблице с ограничением `UNIQUE` | `student_passports.student_id` ➔ `student.student_id` |
| **1 : N** | Один ко многим | В дочерней таблице (на стороне N) | `student.univ_id` ➔ `university.univ_id`<br>`lecturer.univ_id` ➔ `university.univ_id` |
| **M : N (Junction)** | Многие ко многим | В отдельной связующей таблице (только FK) | `subj_lect (lecturer_id, subj_id)` |
| **M : N (Associative)** | Ассоциативная сущность | В отдельной таблице + с доп. данными | `exam_marks (student_id, subj_id, mark, exam_date)` |
| **Рекурсия** | Самоссылка / Иерархия | В той же самой таблице (`NULL` разрешен) | `student.leader_id` ➔ `student.student_id`<br>`lecturer.manager_lecturer_id` ➔ `lecturer.lecturer_id`<br>`employee.manager_id` ➔ `employee.emp_id` |
